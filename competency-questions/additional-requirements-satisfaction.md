# Functional Requirements Satisfaction

This document maps each functional requirement (FR-01 through FR-10) from the MQTO paper (Section 3) to the ontology constructs that satisfy it.

| Req. ID | Requirement | How Satisfied |
|---------|-------------|---------------|
| FR-01 | Box constraints for metrics are sufficient for the current scope. | `mqto:lowerBound` and `mqto:upperBound` properties on `Metric` provide box constraint semantics for threshold-based failure detection. |
| FR-02 | Actual items should carry identifiers (UIDs). | `mqto:identifier` (a native OWL datatype property, aligned with `dcterms:identifier` via `rdfs:seeAlso`) enables unique identification of actual-layer instances (`PhysicalMachine`, `PhysicalMaterial`, `MethodExecution`) for correlation with external systems such as ERP, MES, and SCADA. |
| FR-03 | Timestamps and notes should be recorded for all kinds of events. | Timestamp properties (`mqto:occurrenceTime`, `mqto:calculatedTime`, `mqto:startTime`, `mqto:endTime`, `mqto:abortedTime`, `mqto:completionTime`) cover temporal tracking across all event types. Freetext notes can be attached to any instance using standard annotation properties such as `skos:note` or `rdfs:comment`, requiring no additional MQTO-specific property. |
| FR-04 | The ontology must explicitly connect quality-management concepts, production-system context, and data-infrastructure entities. | The Ishikawa structure (Machine/Material/Method) explicitly connects quality management (Failure, Countermeasure), production context (MethodExecution, participants), and data infrastructure (Signal, Observation, Metric). The `mqto:Signal` class serves as the key bridge between specified metrics and actual observations. |
| FR-05 | The model must distinguish generic specifications from actual concepts. | LIS specified/actual pattern systematically distinguishes schemas (`Metric`, `FailureMode`, `Countermeasure`) from instances (`MetricAssessment`, `FailureOccurrence`, `CountermeasureExecution`) via `lis:implements` relationships. |
| FR-06 | Key relations must be modeled so that conclusions remain explainable. | Explicit object properties model explainable relationships: `mqto:refersToMetric` (failure-metric diagnostic links), `mqto:causes` with strength variants (causal chains), `mqto:mitigatedBy` (failure-countermeasure links), `mqto:raised` (metric-to-failure detection). |
| FR-07 | Measurements, actuations and indicators must be interpreted together with process context. | Integration of LIS production context ensures metrics and failures are always contextualized by machine, material, and method execution. `PhysicalMachine` and `PhysicalMaterial` are `sosa:FeatureOfInterest`, linking observations directly to physical entities. `MethodExecution` subclasses `lis:Activity`, enabling `lis:hasParticipant` links to its physical participants. |
| FR-08 | The ontology should be modular and extensible. | Modular architecture: `FailureSourceCategory`/`FailureSource` hierarchy enables domain-specific equipment and material subclasses; Signal and Metric allow adding new data channels and KPIs; Countermeasure supports procedure libraries. No changes to core connector structure required for domain extension. |
| FR-09 | Modeling patterns should support practical queryability. | SPARQL-friendly design: direct properties instead of complex property paths, OWL-native List instead of blank-node Collections, explicit inverses for bidirectional navigation. All 13 competency questions are answerable via standard SPARQL 1.1 queries. |
| FR-10 | Failure modes and countermeasures should be equipped with weights. | `mqto:weight` datatype property on `FailureMode` and `Countermeasure` supports weighted ranking compatible with FMEA-style prioritization methods. |
